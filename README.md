# ounce-central — أوقية / الإدارة المركزية

تطبيق فرونت إند **منفصل تمامًا** عن `ounce-frontend` (تطبيق الفرع)، مخصَّص
للمستخدم المركزي لكل متجر مشترك في منصة أوقية (`store_users`، لا
`users`).

## الفكرة

منصة أوقية منصة SaaS متعددة المستأجرين (multi-tenant):

- **الفرع** (`ounce-frontend`) — التطبيق التشغيلي اليومي داخل كل فرع
  (مبيعات، مخزون، كسر، خزنة...).
- **المركزي** (هذا المشروع) — يفتحه صاحب/موظفو المتجر لإدارة فروعهم:
  عرض الفروع، تقرير مجمّع لكل الفروع، وإنشاء فرع جديد ضمن سقف الاشتراك.
- **الأدمن** (لم يُبنَ بعد) — لإدارة المنصة نفسها عبر كل المتاجر
  (الاشتراكات، الحدود، التفعيل/الإيقاف).

هذا التطبيق يتصل **بنفس الباك إند الحقيقي** الذي يخدم تطبيق الفرع (نفس
قاعدة PostgreSQL)، عبر مسارات مخصَّصة:

- `POST /api/store-auth/login` — دخول بالبريد وكلمة المرور
- `GET /api/store-auth/me` — استعادة الجلسة
- `GET /api/store/branches` — فروع المتجر الحالي
- `GET /api/store/report?period=YYYY-MM` — تقرير مجمّع
- `POST /api/store/branches` — إنشاء فرع جديد (owner فقط، ضمن سقف
  `stores.max_branches`)

راجع `storeAuth.routes.js` و`store.routes.js` في الباك إند للتفاصيل
الكاملة.

## التشغيل محليًا

```bash
npm install
cp .env.example .env   # واضبط VITE_API_URL إن لزم
npm run dev
```

## البناء للإنتاج

```bash
npm run build   # يبني إلى dist/ وينسخ serve.json معه
npm start        # يشغّل dist/ عبر serve (يقرأ $PORT)
```

## ملاحظة أمنية مهمة

لا يوجد بعد أي طريق لإنشاء أول حساب `owner` لمتجر إلا عبر مسار مؤقت
محمي بمفتاح سري (`POST /api/store-auth/bootstrap-owner` +
`PLATFORM_ADMIN_KEY`) — يُستخدم يدويًّا (Postman مثلًا) حتى يُبنى تطبيق
الأدمن الحقيقي. لا واجهة له في هذا التطبيق عمدًا.
